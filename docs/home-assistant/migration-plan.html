1. Feasibility verdict

Feasible, including full Homebridge removal and running HA on the existing Pi 4. Every device has a maintained HA integration. The Zigbee dongle you already own makes Home Assistant independent of both Aqara hubs: Aqara blind motors, radiator thermostats and sensors are well supported by Zigbee2MQTT. Apple Home stays as the iPhone/Siri remote, fed by HA's HomeKit Bridge. All automations move to HA.

  • Dyson HP04 (Pure Hot+Cool) is a supported model in ha-dyson (libdyson-wg). It uses local MQTT after a one-time cloud credential fetch.
  • Klarta Humea has a dedicated profile in tuya-local (klarta_humea_humidifier.yaml) and runs fully locally.
  • Govee on the cloud path needs no extra network leg. Use the govee2mqtt add-on with a Govee API key.

What changes because HA goes on the same Pi

Homebridge and HA cannot run side by side on one Pi 4. Re-imaging it in place would be a big-bang cutover with no quick way back. The plan avoids that with two cheap measures:

  1. Never overwrite the Homebridge boot medium. HAOS goes on a new USB SSD (or new SD card). The current Homebridge card is pulled, labelled and stored. Rollback becomes a 5-minute media swap.
  2. "Bridge-lift": move Homebridge temporarily to a Proxmox LXC, restored from its own backup (same HomeKit identities, so Apple Home does not notice). That frees the Pi for HA while Homebridge keeps serving Apple Home. Devices then move to HA one batch at a time, each with its own rollback. The LXC is deleted at the end.

3. Target architecture

Design principles

  1. One device, one owner. Each device has exactly one controlling integration and appears in Apple Home exactly once.
  2. Native HomeKit stays native only for Hue (multi-controller). Everything else reaches Apple Home through the HA bridge.
  3. All automations live in HA, versioned in Git.
  4. Never destroy a working state until its replacement has soaked. The Homebridge SD card, the Homebridge backups and the Aqara hub all survive until Phase 9.

4. Cutover strategy: one Pi, two systems

Phase 1–2Back up, inventory. Nothing changes.
Phase 3 · bridge-liftHomebridge restored into Proxmox LXC 112. Pi shut down, SD pulled and stored.
Phase 4HAOS on the Pi 4 from a new SSD, at the same IP .155.
Phase 5Additive integrations + Klarta, Dyson, Govee in HA.
Phase 6Batches: WoL retired → Govee → Daikin → leftovers. Homebridge shrinks to zero.
Phase 7Aqara devices hub → Zigbee2MQTT, room by room.
Phase 8Remaining automations into HA.
Phase 92-week burn-in, then delete LXC, retire hubs, wipe the old SD after 30 days.

Why not re-image the Pi directly? You could: back up, flash HAOS, rebuild everything in one weekend. But from the moment the Pi reboots, every Homebridge accessory is "No Response". Daikin and Govee would be dark until HA is fully set up and re-paired, and any surprise (a Daikin OAuth re-consent, a Govee API key issue) extends the outage. Bridge-lift costs about 1 evening and turns that into small reversible steps. If you prefer the big-bang anyway, skip Phase 3. The recovery runbook covers both.

7. Migration phases

Each phase ends with a gate (what must be true to continue) and a rollback. The full recovery procedures are in section 8.

Phase 0 · Prerequisites and shopping ½ evening no impact

  1. Hardware:
    • A USB 3 SSD (any 64–256 GB SATA SSD in a UASP enclosure, or a small USB SSD) or a new high-endurance 32–64 GB SD card.
    • A USB 2 extension cable (≥ 50 cm) for the Zigbee dongle. USB 3 ports and SSDs emit 2.4 GHz noise that cripples Zigbee, so the dongle must not sit next to the SSD.
    • A label and a bag for the Homebridge SD card.
  2. Prepare the SONOFF Dongle Plus E (EFR32MG21). From the dev PC, flash the current EmberZNet NCP coordinator firmware (not router or Thread/multiprotocol firmware) with SONOFF's web flasher or the Silabs firmware builder releases. Note the version in compute/homeassistant_pi/notes.md; Z2M's ember driver expects EmberZNet ≥ 7.4.
  3. Pi 4 bootloader: USB boot has been the default since 2020 EEPROMs. If the Pi has never been updated, the Raspberry Pi Imager → Misc utility images → Bootloader → USB Boot card fixes it. Flashing that utility card does not touch the Homebridge card.
  4. Vaultwarden items (values only in Vaultwarden, never in the repo): homelab/homeassistant/owner, …/backup-encryption-key, …/homekit-bridge-setup-code, …/daikin-developer-app, …/tuya-klarta, …/dyson, …/govee-api-key, …/lg-thinq-pat, …/dreame, …/mqtt-users, …/token-homepage.
  5. Govee API key: request it in the Govee Home app (Profile → Settings → Apply for API Key); it arrives by email.
  6. Daikin: create a separate app in the Daikin Developer Portal for HA. The redirect URI is given in the daikin_onecta README.
Gate: hardware on the desk, dongle model known and flashed, keys in Vaultwarden.

Phase 1 · Back up and freeze 1 evening no impact

1a. Homebridge

  1. Run the backup job on demand: TrueNAS UI → System → Advanced → Cron Jobs → homebridge-backup → Run Now (or on the NAS: midclt call cronjob.run 21). Check that the Kuma push monitor backup-homebridge-dump turned green.
  2. Second, independent copy: Homebridge UI → Settings → Backup → Download Backup. gpg-encrypt it with the dump passphrase and store it in /mnt/bulk/backups/homebridge/pre-ha-migration/ (outside the 56-day retention, kept indefinitely).
  3. Restore-drill steps 1–2 from nas/restore-drills/homebridge-restore.md: decrypt and tar -tzf. You need a backup that is proven readable before Phase 3 depends on it.
  4. Write down in Vaultwarden the setup PIN of the main bridge and of each child bridge (Homebridge UI → Status QR/PIN; child bridges under each plugin's bridge settings). Rollback needs them if a bridge is ever removed from Apple Home.

1b. Apple Home "export" (manual, there is no API)

  1. Screenshot every room (names and placement).
  2. Automation tab: for every automation record trigger, conditions, actions, enabled in the mapping sheet (2b).
  3. Every scene: members and target states (brightness, colour, AC mode/temperature, blind position).
  4. Home settings → Hubs & Bridges: screenshot the list.
  5. Note iPhone Shortcuts personal automations that touch Home.

1c. Aqara "export"

  1. Aqara Home app: for every device under hub #1 record model, name, room, battery/mains, and for blinds the calibrated limits and direction, for thermostats the schedules, setpoints, offsets, window-detection setting.
  2. Export any Aqara-app automations (Aqara app → Automation) to the sheet; they run on the hub, independent of Apple, and will stop when the device leaves the hub.
  3. Store all of 1b and 1c in the Obsidian vault (Home/HA migration/) so it is searchable through vault-rag.

1d. Freeze

No new accessories in Homebridge, Apple Home or Aqara until the end. New devices go straight to HA.

Gate: two Homebridge backups, one proven readable, one outside retention. Bridge PINs in Vaultwarden. Apple and Aqara inventories complete.

2a. What Homebridge really runs (prints names only, never secrets)

On the dev PC, in a real terminal (the ! prefix has no stdin for the gpg passphrase prompt). Do not cat config.json: it contains plugin credentials.

2c. Zigbee mesh plan

Phase 3 · Bridge-lift: Homebridge → temporary Proxmox LXC optional since v0.5, skipped by default

Skipped by default. With only 6 relevant accessories, the direct swap costs one evening of Govee and Daikin showing "No Response" in Apple Home. Do not remove the old bridges from Apple Home until HA's bridge works (Phase 6), so the SD-card swap stays a complete rollback. Use the steps below only if that evening is unacceptable. Elsewhere in this document, everything that mentions LXC 112 applies only when the bridge-lift is used.

Goal: Homebridge keeps serving Apple Home with the same HomeKit identities from a container, so the Pi is free. The backup contains the bridge usernames, pairing keys and persist/, which is what makes Apple Home accept the moved bridge without re-pairing.

  1. On Proxmox, create a Debian 12 LXC on VLAN 1: 
    pveam update
pveam available --section system | grep debian-12
pveam download local debian-12-standard_<ver>_amd64.tar.zst
pct create 112 local:vztmpl/debian-12-standard_<ver>_amd64.tar.zst \
  --hostname homebridge-temp --cores 2 --memory 1024 --swap 512 \
  --rootfs local-lvm:8 --net0 name=eth0,bridge=vmbr0,ip=dhcp \
  --unprivileged 1 --features nesting=1 --onboot 1
pct start 112
    Then create a UDR DHCP reservation for its MAC on Default (VLAN 1), e.g. 192.168.1.<HBT>.
  2. Inside (pct enter 112), install Homebridge from the official apt repository (two plain commands, no heredoc): 
    apt update && apt install -y curl gpg
curl -sSfL https://repo.homebridge.io/KEY.gpg | gpg --dearmor -o /usr/share/keyrings/homebridge.gpg
echo "deb [signed-by=/usr/share/keyrings/homebridge.gpg] https://repo.homebridge.io stable main" > /etc/apt/sources.list.d/homebridge.list
apt update && apt install -y homebridge
    Open http://192.168.1.<HBT>:8581. Create a throwaway admin; the restore will replace it.
  3. Stop the Pi's Homebridge cleanly: Pi UI → top-right power menu → Shut Down. Wait until the green LED stops, then unplug power. Two instances with the same HomeKit identity must never run at once.
  4. Remove the Pi's SD card, label it "HOMEBRIDGE, DO NOT WIPE, <date>", and store it. This is rollback R1.
  5. In the LXC UI: Settings → Backup → Restore Backup → upload the decrypted backup from Phase 1. Homebridge reinstalls plugins (needs internet) and restarts. Log in again with the original admin credentials (from Vaultwarden).
  6. Watch the logs until the main bridge and child bridges (Govee, daikin-cloud, WoL) say they are advertising. Daikin: if the plugin reports an expired or invalid token, re-run its OAuth login in the plugin settings. If its redirect URI was bound to the Pi's IP, update the redirect in the Daikin Developer Portal app used by Homebridge.
  7. iPhone, Home app: every Homebridge accessory should come back from "No Response" within about 1–5 minutes (Apple finds the bridges by mDNS, not by IP). Test one Govee light and one Daikin unit, locally and on mobile data.
  8. Repoint homelab plumbing to the LXC (temporary):
    • Caddy @homebridge: reverse_proxy → http://192.168.1.<HBT>:8581 (both the /health handle and the main one). Commit, push, make deploy-caddy, force-recreate.
    • NAS /root/.backup-env: add HOMEBRIDGE_HOST=http://192.168.1.<HBT>:8581 (the script sources this file after setting its default, so the value overrides). Run cron 21 once and check Kuma.
    • Kuma homebridge-ping → the LXC IP. Homepage widget URL → LXC IP.
Gate: all Homebridge accessories respond in Apple Home with no re-pair prompt, for 24 h. The backup job works against the LXC.
Rollback (R1): pct stop 112 → put the labelled SD card back in the Pi → power on. It is byte-for-byte the pre-migration state. Revert the Caddy, backup-env and Kuma repoints.

Phase 4 · Install Home Assistant OS on the Pi 4 1 evening no Apple Home change

  1. On the dev PC, Raspberry Pi Imager → Other specific-purpose OS → Home assistants and home automation → Home Assistant → Home Assistant OS (RPi 4) → write to the new SSD or SD card. Never the labelled Homebridge card.
  2. Plug in the SSD (blue USB 3 port) and the Zigbee dongle on the USB 2 extension (black USB 2 port, dongle at least 50 cm away from the SSD). Connect Ethernet, then power on. The Pi keeps its MAC, so it gets 192.168.1.155 from the existing reservation.
  3. http://192.168.1.155:8123 → wait for the first-boot download → onboarding: owner account (Vaultwarden), location, metric, Europe/Warsaw. Then Profile → Security → enable TOTP MFA.
  4. Settings → System → Updates: switch off automatic updates for Core, OS and add-ons. You update manually after a backup.
  5. Add-ons: File editor, Terminal & SSH (key-only: your ~/.ssh/id_ed25519.pub), Mosquitto broker (create users z2m, govee2mqtt, homeassistant; passwords in Vaultwarden), Get HACS (finish the GitHub device flow).
  6. Recorder hygiene, important on a Pi. In configuration.yaml: 
    recorder:
  purge_keep_days: 10
  commit_interval: 5
http:
  use_x_forwarded_for: true
  trusted_proxies:
    - 192.168.1.252
homeassistant:
  external_url: https://ha.mati-lab.online
  internal_url: http://192.168.1.155:8123
    Restart.
  7. Caddy: new @homeassistant host ha.mati-lab.online → reverse_proxy http://192.168.1.155:8123, no forward_auth (with a comment explaining why, as on Vaultwarden), no Cloudflared route. Deploy, then force-recreate.
  8. Backups:
    • NAS: create a share for HA backups (e.g. dataset bulk/backups/homeassistant, SMB or NFS, restricted to 192.168.1.155).
    • HA → Settings → System → Storage → Add network storage (usage: Backup) → Backups → automatic daily, keep 14, encrypted (key in Vaultwarden …/backup-encryption-key, also printed and stored offline). The key is the only way to restore.
    • Take a manual backup now and confirm it is on the NAS.
  9. Monitoring: Kuma homeassistant-http → https://ha.mati-lab.online/manifest.json. The existing homebridge-ping already points at the LXC; add homeassistant-ping for 192.168.1.155. Homepage: Home Assistant tile with the homeassistant widget (token in Pi network/.env as HOMEPAGE_VAR_HA_TOKEN), then restart Homepage.
  10. nas/secrets-inventory.md: Home Assistant section (placeholders only). New Gitea repo homeassistant-config (D6).
  11. Install the HA Companion app on the household iPhones (push notifications and presence).
Gate: HA reachable at https://ha.mati-lab.online with MFA. An encrypted backup is on the NAS. Kuma is green. Homebridge in the LXC is unaffected.
Rollback: power off the Pi, unplug the SSD. Nothing else depends on HA yet. Full R1 if you also want the Pi back as Homebridge.

  5. Fallbacks: core Tuya (cloud) → open a tuya-local issue with the DP dump → ESP32 UART mod.

5c. Dyson HP04 (ha-dyson)

  2. HACS → custom repository libdyson-wg/ha-dyson → install → restart.
  3. Add Dyson → cloud account → email plus OTP. This fetches the HP04's serial and local credentials once.

  6. Fallback: cmgrayb/hass-dyson.

5d. Govee (govee2mqtt, cloud)

  1. Add the add-on repository for wez/govee2mqtt → install the add-on → config: Govee API key, optionally Govee email/password (enables the faster AWS IoT push path), MQTT host core-mosquitto with user govee2mqtt.
  2. Start it. The three lights appear as MQTT devices. Do not remove the Homebridge Govee bridge yet. Running both against the cloud API for a few days is fine at this scale (the Govee API allows 10,000 requests a day).
Gate: every new integration controls its device from HA and survives an HA restart and a device power-cycle. Apple Home is unchanged.
Rollback: delete the integration or add-on in HA. Nothing outside HA changed.

Phase 6 · Cutover: Homebridge → HA HomeKit Bridge 1 batch per evening user-visible

6a. One-time: create the HA HomeKit Bridge

  1. Settings → Devices & services → Add → HomeKit Bridge, mode bridge, name HA Bridge. In Configure choose include entities: start with one test entity.
  2. Apple Home → Add Accessory → scan the QR code from the HA notification. Save the setup code in Vaultwarden.
  3. Check it responds from VLAN 20 Wi-Fi and from mobile data.
  4. Consider a second bridge for climate (Daikin, thermostats, Dyson, Klarta) so a reset of one bridge never wipes all rooms and scenes at once.

6b. Batches

BatchContentsSpecial handling
B1Retire WoLApple Home → remove the "Homebridge WoL" bridge → Homebridge LXC: disable or uninstall the WoL plugin. No HA replacement. Remove WoL from any scenes.
B2Govee ×3Standard procedure
B3Daikin ×3First disable the Homebridge daikin-cloud child bridge, then add daikin_onecta to HA. Never two pollers on one 200/day quota. Keep HA polling ≤ about 150/day (default 15 min; high-frequency only while running). Never retry while rate-limited: the lockout grows.
B4Main-bridge leftoversPer the 2a inventory
B5Klarta, Dyson, Dreame (optional)New to Apple, so additive only

6c. Standard per-batch procedure

  1. From the sheet, list every Apple scene and automation using this batch's accessories.
  2. Add the batch's HA entities to the HomeKit Bridge include list. Rename them exactly as in Apple Home today (Siri depends on the names).
  3. Apple Home: put the new accessories into the correct rooms and fix their icons and types.
  4. Apple Home: remove the old Homebridge child bridge (Home settings → Hubs & Bridges → bridge → Remove Bridge from Home). Homebridge LXC: disable that child bridge.
  5. Re-add the new accessories to the scenes and automations from step 1. Apple silently removed the old ones in step 4.
  6. Move any Apple automation whose devices are now all in HA into HA in the same session (Phase 8 procedure), so nothing is half-migrated.
  7. Test: Home app, one Siri command per device, one scene, remote off Wi-Fi. Soak 48 h before the next batch.
Gate: after B4, the Homebridge LXC serves zero accessories, and the HA bridge has run 48 h clean.
Rollback (R2, per batch): remove the entities from the HA bridge include list (for Daikin, disable the HA integration first). Re-enable the child bridge in the LXC and re-add it to Apple Home with the PIN from Vaultwarden. Re-assign rooms and scenes from the sheet.

Phase 7 · Aqara devices → Zigbee2MQTT 1–2 evenings user-visible, room by room

7a. Zigbee2MQTT setup

  1. Add the Zigbee2MQTT add-on repository → install Zigbee2MQTT.
  2. Config: MQTT mqtt://core-mosquitto:1883, user z2m. Serial port by /dev/serial/by-id/usb-…Sonoff_Zigbee_3.0_USB_Dongle_Plus… (stable across reboots), adapter: ember, baudrate: 115200, rtscts: false. Channel from 2c. homeassistant: enabled: true. Generate a new network_key (Z2M does it on first start; it is in the HA backup).
  3. Start it, open the Z2M panel, and enable Permit join only while pairing.
  4. Pilot: pair one non-critical Aqara sensor first. Leave it 24 h and check that it keeps reporting (Aqara devices are the classic "pairs fine, drops after an hour" case).

7b. Per-device move (repeat room by room: Z1 sensors → Z2 thermostats → Z3 blinds)

  1. Aqara Home app: remove the device from hub #1. This also removes it from Apple Home and from Aqara-app and Apple automations.
  2. Reset the device (sensors: hold the button about 5 s until the LED blinks. Thermostats and blind motors: per model manual, usually a long press of the function button). Bring it within a few metres of the dongle for the interview.
  3. Z2M: Permit join → wait for Interview successful → give it a friendly name like sypialnia_roleta.
  4. Configure:
    • Roller Shade Driver E1: re-set the upper and lower limits (button sequence per the Aqara manual, or the Z2M device page), check direction, test 0/50/100 %, and confirm battery and charging-state reporting.
    • W600: keep it in Zigbee mode (it already is, since it is on the hub; a factory reset keeps the current protocol, so do not switch it to Thread). Run valve calibration; set child lock, window detection and temperature offset. If the Z2M external-temperature option is still missing, use the internal sensor plus an offset, and drive setpoints from an HA automation using a room sensor. Recreate schedules as HA automations or a schedule helper.
    • Sensors: check battery, occupancy timeout, temperature offset.
  5. Add to the HA HomeKit Bridge include list with the same name as before → Apple Home room, then re-add to scenes.
  6. Recreate every Aqara-app and Apple automation that used it in HA (from 1c).
  7. When hub #1 has no devices left: remove it from Apple Home, unplug it and store it with hub #2 until Phase 9.
Gate: all Aqara devices are in Z2M, have reported for 48 h, the Z2M network map shows no orphan devices, and batteries report.
Rollback (R3, per device): Z2M → remove the device → reset it → Aqara Home app → add to hub #1 → re-add to the Apple room and scenes. Blind calibration and thermostat settings must be redone. That is why this phase goes room by room and starts with sensors.

Phase 8 · Remaining automations into HA 1 evening

  1. For each remaining Apple automation, build the HA version. Presence uses Companion-app zones ("first person arrives" or "last person leaves" via zone.home); time and sun use the time/sun triggers; sensors use the Z2M entities.
  2. Test it, then turn off (not delete) the Apple version the same day. Delete it after 14 quiet days.
  3. Add the improvements the migration enables: Klarta water-tank notification; humidity-driven Klarta from Aqara sensors; Daikin or thermostat off when a window sensor opens; blinds by sun elevation; Dyson auto mode from PM2.5.
  4. Commit automations.yaml, scripts.yaml and packages/ to homeassistant-config.
Gate: the Apple Home Automation tab contains only disabled items.

Phase 9 · Burn-in and decommission 2 weeks + ½ evening

Burn-in criteria (14 days)

  • No unexplained "No Response" in Apple Home. No Zigbee device dropped.
  • Every automation fired correctly at least once.
  • Daily HA backups are green on the NAS, and the HA restore drill (R5) has been run once.
  • Survives a planned Pi reboot and a power cut (pull the plug once): HA, Z2M and the bridge come back unattended.

Decommission

  1. Final Homebridge backup from the LXC → pre-ha-migration/ (kept indefinitely).
  2. Apple Home: remove the Homebridge main bridge if still present. Then pct stop 112, wait a week, then pct destroy 112.
  3. NAS: disable cron 21 and remove HOMEBRIDGE_* from /root/.backup-env. Kuma: delete homebridge-http, homebridge-ping and backup-homebridge-dump. Caddy: delete the @homebridge block. Homepage: remove the Homebridge tile and the HOMEBRIDGE_* vars.
  4. Add a Kuma push monitor for the HA backup (an HA automation on backup completion → rest_command to the Kuma push URL), so HA backups are watched like every other dump.
  5. secrets-inventory.md: mark the Homebridge rows retired. Rotate or delete the Govee and Daikin Homebridge credentials (separate Daikin developer app → delete it).
  6. Aqara hubs #1 and #2: factory-reset and sell or give away, or keep one as an emergency spare.
  7. Labelled Homebridge SD card: keep for 30 days after decommission, then wipe it.
  8. Docs: global ~/.claude/CLAUDE.md box table (Homebridge Pi → Home Assistant Pi, SSH via the add-on on port 22222 or 22 per configuration), docs/followups.md, the network notes that mention Homebridge, and a new nas/restore-drills/homeassistant-restore.md.

8. Recovery runbook

Ordered from "something just went wrong" to "everything is gone". Each scenario lists what you need and how long it takes.

IDSituationRecoveryNeedsTime
R1Anything goes wrong in Phases 3–5, or you want to abort the migration before any Apple Home change
  1. pct stop 112 (the Homebridge LXC must be off: one identity, one instance).
  2. Pi: shut down HA (Settings → System → Power → Shut down), unplug power, unplug the SSD.
  3. Insert the labelled Homebridge SD card and power on.
  4. Home app: accessories respond again within minutes, with no re-pair needed (same identity, untouched card).
  5. Revert the Caddy upstream, HOMEBRIDGE_HOST in /root/.backup-env, and the Kuma and Homepage targets to 192.168.1.155.
Labelled SD card~10 min
R1bSD card lost or corrupt, and you need Homebridge on the Pi
  1. Flash the latest Homebridge Raspberry Pi Image with Raspberry Pi Imager (Other specific-purpose OS → Home assistants and home automation → Homebridge) to any SD card.
  2. Boot it, finish the wizard with a placeholder admin, then Settings → Backup → Restore Backup using the newest backup (decrypt as in nas/restore-drills/homebridge-restore.md).
  3. Log in with the original admin. Plugins reinstall. Bridges keep their identities, so no re-pair is needed unless a bridge was removed from Apple Home (then re-add it with its PIN from Vaultwarden).

R5HA itself broken (bad update, corrupt SSD) after cutover
  1. Settings → System → Backups → restore the latest backup from before the update (if HA still boots).
  2. If not: re-flash HAOS (RPi 4) onto the SSD (or a spare) → onboarding screen → "Restore from backup" → upload the newest file from the NAS share → enter the backup encryption key.
  3. The backup contains the HomeKit Bridge pairing, Z2M (network_key, PAN ID, device database) and Mosquitto users. Apple Home accessories and Zigbee devices come back without re-pairing, provided the same dongle is used.
  4. If the dongle died: use another EFR32-based dongle (ideally another SONOFF Dongle Plus E) with the same firmware family. After the restore, Z2M uses the stored coordinator_backup.json to rebuild the network on the new stick (supported by the ember driver). Without the backup, every Zigbee device must be re-paired. A spare dongle (~€25) in the drawer is cheap insurance.
HA backup on NAS + encryption key, spare SSD/SD~45 min
R6Pi 4 hardware deadAny Pi 4/5 (or temporarily a Proxmox VM with HAOS and the dongle passed through): R5 step 2 onto it. The DHCP reservation is MAC-bound, so either update it in the UDR to the new MAC at .155 or change Caddy, Kuma and Homepage targets.As R5~1 h
Golden rules during recovery
  • Never run two Homebridge instances restored from the same backup at the same time: duplicate HomeKit identities confuse Apple Home and can force a full re-pair.
  • Never run two Zigbee coordinators with the same network key and PAN ID.
  • Never let Homebridge and HA both poll Daikin.
  • Never factory-reset an Aqara hub while devices are still paired to it: that wipes its Zigbee mesh.
